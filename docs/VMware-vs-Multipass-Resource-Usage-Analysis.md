# VMware vs Multipass — 실측 리소스 사용량 분석

`docs/VMware-to-Multipass-Cluster-Migration.md`로 마이그레이션을 진행하면서 각 단계에서 실측한 메모리 수치를 모아 "정말 좋아졌는가, 좋아졌다면 어떤 의미로 좋아졌는가"를 정리한다. 결론부터 말하면 **지표에 따라 결과가 갈린다** — 뭉뚱그려 "좋아졌다"고 하기보다 어떤 지표가 실제로 의미 있는지 구분해서 본다.

## 1. VM 자체 설정값

| | VMware (기존) | Multipass (신규) |
|---|---|---|
| 마스터 | 2.5GB / 2vCPU | 3GB / 2vCPU |
| 워커 ×2 | 각 1.5GB / 2vCPU | 각 1.5GB / 1vCPU |
| **합계** | **5.6GB** | **6GB** |

신규 쪽이 오히려 **400MB 더 할당**했다. 마이그레이션 계획 단계에서 "여유 있게 잡아달라"는 요청에 따라 의도적으로 VMware 대비 더 넉넉한 스펙으로 잡았기 때문 (자세한 내용은 마이그레이션 기록 문서 2절).

## 2. 호스트 여유 메모리 (raw free) — 겉보기엔 더 나빠 보임

| 시점 | 호스트 여유 메모리 |
|---|---|
| VMware 3대 풀가동 중 (마이그레이션 착수 직전) | ~260MB |
| VMware 3대 종료 직후 | ~3.6GB |
| Multipass 3대 + ArgoCD + 앱 전체 풀가동 중 (마이그레이션 완료 시점) | **~64MB** |

이 지표만 보면 신규 쪽이 더 안 좋다. 이유는 세 가지다.

1. VM에 애초에 400MB를 더 할당했다 (1절).
2. 측정 시점이 다르다 — VMware 쪽 260MB는 "그냥 켜져 있는" 상태에서 잰 값이고, Multipass 쪽 64MB는 ArgoCD 전체 컴포넌트 + kafka + postgres + target-tracking-service가 **활발히 동작 중인** 상태에서 잰 값이다.
3. macOS의 "free" 페이지 수치는 원래 낮게 유지되는 게 정상이다. 안 쓰는 RAM을 디스크 캐시로 적극 활용하는 구조라, free가 낮다고 곧 pressure가 심하다는 뜻이 아니다. 실제 압박 여부는 swap 사용량이나 `memory_pressure`의 경고 레벨로 봐야 한다.

**즉, "호스트에 남는 메모리 총량"은 이번 마이그레이션으로 늘어난 게 아니다.** 오히려 대충 비교하면 줄어든 것처럼 보이는데, 그건 측정 조건이 달라서 생긴 착시에 가깝다.

## 3. 진짜 의미 있는 지표 — 게스트 내부 swap 사용량

동일 스펙(워커, ~1.5GB) 끼리 비교한 결과.

| | VMware 워커 (server2) | Multipass 워커1 | Multipass 워커2 |
|---|---|---|---|
| used | 941Mi | 777Mi | 916Mi |
| available | 511Mi | 674Mi | 535Mi |
| **swap 사용량** | **89Mi / 2GB (4.5%)** | **0.26Mi (~0%)** | **8.6Mi (0.4%)** |

기존 VMware 워커는 **평상시 운영 중에도 이미 swap을 4.5% 쓰고 있었다.** 이건 `docs/K3s-Node-Resource-Planning-Troubleshooting.md`에 기록된 "워커가 랜덤하게 NotReady로 빠지는 OOM 연쇄 장애"의 배경(스왑 압박 → 커널이 멎어 네트워크 스택까지 응답 불가 → kubelet 하트비트 끊김 → NodeNotReady)과 정확히 일치하는 패턴이다.

신규 워커는 ArgoCD 전체 컴포넌트 + 앱 스택이 도는 상태에서도 swap을 사실상 쓰지 않는다.

## 4. 그래서 "쓸 수 있는 메모리 공간"이 늘어난 건가?

**아니다.** 8GB 호스트 RAM 총량은 그대로다. 이번에 확인된 건 다음 두 가지로 나눠서 봐야 한다.

### 4.1 늘어나지 않은 것

- 호스트가 실제로 갖고 있는 물리 메모리 총량 (8GB 그대로)
- "여유분을 새 워크로드에 얼마든지 써도 된다"는 의미의 헤드룸 — 오히려 아래 4.3절 이유로 **좁아진 면도 있음**

### 4.2 좋아진 것 — 같은 워크로드를 돌릴 때의 "안전 마진"

같은 양의 워크로드(kafka + postgres + redis + target-tracking-service)를 돌리는 데 필요한 swap 압박이 4.5% → ~0%로 줄었다. 마이그레이션 전체 과정(ArgoCD 재설치, 대형 이미지 pull, Spring Boot 앱 콜드 스타트 등 부하가 몰리는 구간 포함) 동안 **OOM이나 노드 다운이 한 번도 없었다.** 이게 실질적인 안정성 개선이며, "메모리가 늘었다"보다 "같은 메모리로 더 안정적으로 돈다"에 가깝다.

### 4.3 오히려 좁아진 것 — 마스터 taint로 인한 스케줄링 범위 축소

마이그레이션 중 `node-role.kubernetes.io/master=:NoSchedule` taint를 신규 클러스터에 새로 적용했다 (기존 클러스터엔 없었음, 과거 장애 재발 방지책으로 적용 — 마이그레이션 기록 문서 5.3절).

- **기존**: taint 없음 → 앱 파드가 3노드(마스터 포함) 어디든 배치 가능, 사실상 5.6GB 전체가 스케줄링 대상.
- **신규**: taint 적용 → 앱 파드는 워커 2대(합계 3GB)에만 배치 가능. ArgoCD 전체 컴포넌트까지 이 3GB 안에 같이 들어가야 한다.

즉, **향후 `defense-api-gateway` 같은 워크로드를 추가로 배포하려면, 호스트 전체 8GB가 아니라 "워커 2대 3GB"가 진짜 예산이라는 점을 봐야 한다.** 이건 이번 마이그레이션으로 인해 오히려 더 타이트해진 제약이다.

## 5. 결론 요약

| 질문 | 답 |
|---|---|
| 호스트에 남는 메모리 총량이 늘었나? | 아니오. 오히려 VM에 400MB 더 할당해서 순수 여유분은 비슷하거나 측정 시점 차이로 더 좁아 보임 |
| 같은 워크로드를 더 안정적으로 돌릴 수 있게 됐나? | **예.** swap 압박이 4.5%→~0%로 줄었고, 과거 반복됐던 OOM발 노드 다운 패턴이 이번 마이그레이션 전 과정에서 재현되지 않음 |
| 새 워크로드를 추가할 여유가 늘었나? | **아니오, 오히려 주의가 필요.** 마스터 taint 때문에 앱 워크로드가 배치될 수 있는 노드가 3대→2대(3GB)로 줄었음. 워크로드 추가 시 이 3GB를 기준으로 판단해야 함 (후속 과제는 마이그레이션 기록 문서 7.3절 참고) |
